# Feature Spec — Стерео 3D відео: VR180 SBS та 360 3D TB

**Статус:** draft, готовий до реалізації
**Гілка:** `feature/stereo-3d-180-360`
**Автор запиту:** Richard Kickbush (30 Quest headsets, Австралія) — освітній контент, все виробництво в VR180 3D та 360 3D
**Дата:** 2026-09-09

---

## 0. Короткий зміст (TL;DR для агента)

Треба навчити плеєр показувати **стереоскопічне** 180° і 360° відео з правильним розділенням кадру по очах.

Головне, що треба зрозуміти перед стартом: **це не задача «додати шейдер»**. Поточний пайплайн (`Unity VideoPlayer` → `RenderTexture` → сфера з шейдером) фізично не витягне 8192×4096@60. Стерео-шейдер і півсфера — це ~20% роботи; решта — заміна пайплайну відтворення на композиторний шар Quest (`OVROverlay` + зовнішній `Surface`), плюс модель формату, автовизначення, UI і логістика контенту.

Порядок робіт: спершу **Phase 0 (верифікація заліза)**, і лише потім усе інше. Якщо Phase 0 покаже, що 8K60 не декодується на наявних шоломах — обсяг фічі змінюється кардинально.

## 1. Аналіз реальних семплів замовника

Обидва файли лежать у `Video Samples/` (каталог у `.gitignore`, рядок 138). Розібрані побайтово парсером MP4-боксів (скрипт у Додатку B).

### 1.1 VR180 3D

`1803D 8K60 Sample for Eugen - short_180_LR.mp4`

| Параметр | Значення |
|---|---|
| Контейнер | MP4, brands `isom/iso2/mp41`, `moov` **в кінці** (не faststart) |
| Відео | HEVC `hvc1`, **8192×4096**, Main **10** (profile_idc=2), **10-bit**, Level **6.1**, **main tier** |
| Частота | 945 кадрів / 15.766 с = **59.94 fps** (60000/1001) |
| Бітрейт | **97.4 Мбіт/с** → **730 МБ/хв** → 43.8 ГБ/год |
| Колір | `nclx`: primaries=1, transfer=4, matrix=1 → BT.709, гамма 2.2, **не HDR** |
| Пікселі | `pasp` 1:1 |
| Аудіо | AAC `mp4a`, **2 канали**, 48 кГц, 16 біт — звичайне стерео |
| Треки | video + audio + **timecode (`tmcd`)** |
| Розмір на око | **4096×4096** (SBS) → аспект 1:1 → 180°×180° |
| VR-метадані | Google Spherical **v1** (`uuid ffcc8263-f855-4a93-8814-587a02521fdd`) |

Вміст XML-метаданих:

```xml
<GSpherical:Spherical>true</GSpherical:Spherical>
<GSpherical:Stitched>true</GSpherical:Stitched>
<GSpherical:StitchingSoftware>Blackmagic Design DaVinci Resolve Studio</GSpherical:StitchingSoftware>
<GSpherical:ProjectionType>equirectangular</GSpherical:ProjectionType>
<GSpherical:StereoMode>left-right</GSpherical:StereoMode>
```

> **Критично:** метадані **не відповідають вмісту**. Файл заявлений як `equirectangular` (тобто повна сфера 360°), тоді як реально це VR180. Немає боксів Spherical v2 (`st3d`/`sv3d`/`proj`), немає `equi` з обрізаними межами, немає VR180-меша (`mshp`). Плеєр, що довіриться метаданим, розтягне 180-контент на всю сферу.

### 1.2 360 3D

`Test 360 3D 5.7K clip for Eugen_360_TB.mp4`

| Параметр | Значення |
|---|---|
| Контейнер | MP4, brands `isom/iso2/mp41`, `moov` в кінці |
| Відео | HEVC `hvc1`, **5760×5760**, Main **10**, **10-bit**, Level **6.1**, **high tier** |
| Частота | 2208 кадрів / 73.60 с = **30.0 fps** рівно (timescale 15360, delta 512) |
| Бітрейт | **101.4 Мбіт/с** → **761 МБ/хв** |
| Колір | те саме: BT.709, гамма 2.2, не HDR |
| Аудіо | AAC, 2 канали, 48 кГц |
| Треки | video + audio + `tmcd` |
| Розмір на око | **5760×2880** (TB) → аспект 2:1 → повна сфера 360°×180° |
| VR-метадані | Google Spherical **v1**, `ProjectionType=equirectangular`, `StereoMode=top-bottom` |

Тут метадані **коректні** (це справді 360 TB). Тобто джерело метаданих непослідовне: для 360 воно правильне, для 180 — ні.

### 1.3 Висновки з аналізу

1. **Метаданим довіряти не можна як єдиному джерелу.** Максимум — як підказці нижчого пріоритету.
2. **Ім'я файлу — найнадійніший сигнал.** Обидва файли мають суфікси `_180_LR` і `_360_TB` — це конвенція Meta Quest media, і замовник уже нею користується та згоден її дотримуватись жорстко.
3. **Пропорції дають перевірку**, але лише в парі зі стерео-лейаутом: 2:1 повний кадр = або mono 360, або SBS 180 — розрізнити без імені/метаданих неможливо. Після поділу на око: 2:1 ⇒ 360, 1:1 ⇒ 180.
4. **Обидва файли — 10-bit Main10, Level 6.1**, обидва на межі можливостей мобільних декодерів (33.6 і 33.2 Мпікс на кадр; ліміт L6.1 = 35.65 Мпікс).
5. **Обидва ~100 Мбіт/с.** Це визначальний фактор для логістики: 10-хвилинний матеріал = ~7.3 ГБ на шолом, ×30 шоломів = ~220 ГБ трансферу на сесію заливки.
6. **Звук — звичайне стерео.** Ambisonic наразі не потрібен (але див. §13).
7. **Третій трек `tmcd`** (timecode від Resolve) — має ігноруватись, але це варто перевірити на нативному декодері (індекси треків можуть зсунутись).
8. `moov` **у кінці файлу** — для локального відтворення з диска не проблема, але якщо колись з'явиться стрімінг — треба faststart.

## 2. Цілі та не-цілі

### Цілі

- Відтворення **VR180 3D side-by-side** (лівий кадр зліва) на повну роздільність джерела.
- Відтворення **360 3D top-bottom** (лівий кадр зверху) на повну роздільність джерела.
- Збереження підтримки наявних режимів: **mono 360** і **flat 2D**.
- **Автовизначення** формату при додаванні відео в бібліотеку + **ручне перевизначення** в панелі керування.
- Коректна орієнтація 180-контенту (глядач дивиться в «перед» контенту) і визначена поведінка позаду глядача.
- **Зворотна сумісність**: старі плеєри не ламаються від нових полів; старі конфіги (`videoType: "360"|"2d"`) працюють як раніше.
- **Діагностика можливостей заліза**: плеєр повідомляє серверу, які роздільності/профілі він реально декодує; панель попереджає завчасно.

### Не-цілі (свідомо поза обсягом цієї фічі)

- EAC / cubemap / fisheye проєкції (див. план у `CLAUDE.md` — пріоритет Medium/Low).
- Ambisonic / spatial audio.
- HDR (PQ/HLG) — джерела BT.709 SDR.
- Стрімінг по мережі (усе відтворюється локально з `/sdcard/Movies/`).
- Покадрова синхронізація 30 пристроїв (наявна синхронізація не змінюється; ризик зафіксовано в §11).
- VR180 з мешем (`mshp`) — Google VR180 mesh projection. Наші джерела його не використовують.

## 3. Чому поточний пайплайн не працює

Поточний ланцюг: [`VideoPlayerController.cs`](../../VRClassroomPlayer/Assets/Scripts/Core/VideoPlayerController.cs) → `UnityEngine.Video.VideoPlayer` (`renderMode = RenderTexture`) → `RenderTexture` → [`ViewModeManager.SetRenderTexture()`](../../VRClassroomPlayer/Assets/Scripts/Core/ViewModeManager.cs) → матеріал на сфері/квадраті → [`VideoSphere.shader`](../../VRClassroomPlayer/Assets/Shaders/VideoSphere.shader).

Проблеми, в порядку критичності:

| # | Проблема | Де | Наслідок |
|---|---|---|---|
| 1 | Жорсткий клемп `maxDimension = 4096` | `VideoPlayerController.cs`, метод `ResizeRenderTexture` | 8192×4096 → 4096×4096; на око лишається 2048×4096 замість 4096×4096. Втрачається саме те, заради чого фіча робиться |
| 2 | Повний блит кадру в `RenderTexture` кожен кадр | архітектура Unity VideoPlayer на Android | 8192×4096 ARGB32 = **128 МіБ** на текстуру; при 59.94 fps це ~**8.0 ГБ/с** запису + стільки ж читання при семплінгу ⇒ ~16 ГБ/с трафіку пам'яті поверх декодування. Для 5760×5760@30 — ~4.0 ГБ/с + читання. Мобільна пам'ять Quest такого не витримує |
| 3 | `RenderTextureFormat.ARGB32` — 8 біт на канал | `VideoPlayerController.cs` | Джерело 10-бітне ⇒ бендінг на градієнтах (небо, стіни, тумани) |
| 4 | Подвійний ресемплінг | RT → меш → окуляр | Втрата різкості навіть там, де роздільності вистачає |
| 5 | Unity VideoPlayer + 10-bit HEVC L6.1 на Android | прошарок Unity | Історично нестабільно: від чорного кадру до тихого фолбеку на софтверний декодер. Перевіряється **лише на пристрої** |
| 6 | Немає геометрії півсфери | `ViewModeManager.CreateDisplay()` | Unity не має примітиву півсфери — треба генерувати меш |
| 7 | Немає per-eye UV | `VideoSphere.shader` | `unity_StereoEyeIndex` не використовується; обидва ока бачать увесь кадр |

**Висновок:** правильний шлях для 8K на Quest — той, яким користується сам Meta Media Player: декодер (Android `MediaPlayer`/ExoPlayer) віддає кадри **напряму в `Surface`, що належить композиторному шару `OVROverlay`** типу `Equirect`, з окремими per-eye source rect для LR/TB. Тоді проміжного `RenderTexture` і блиту немає взагалі, композитор семплить текстуру сам, з кращою якістю і меншою затримкою.

## 4. Модель формату (доменна модель)

### 4.1 Рішення: розділити на ортогональні осі

Плаский enum на 8 значень (як у чернетці плану в `CLAUDE.md`) призводить до комбінаторного вибуху. Замість цього:

```csharp
namespace VRClassroom
{
    public enum VideoProjection
    {
        Flat,          // площина перед глядачем
        Hemisphere180, // 180°×180°, equirect на око
        Sphere360,     // 360°×180°, equirect на око
        None           // логотип / ідл
    }

    public enum StereoLayout
    {
        Mono,          // один кадр на обидва ока
        SideBySide,    // ліве око — ліва половина
        TopBottom      // ліве око — верхня половина
    }

    [Serializable]
    public class VideoFormat
    {
        public VideoProjection projection = VideoProjection.Sphere360;
        public StereoLayout    stereo     = StereoLayout.Mono;
        public bool            swapEyes   = false;  // для матеріалу з переставленими очима
        public float           forwardYaw = 0f;     // зсув «переду» контенту в градусах
        public float           verticalFovDeg = 180f; // 180 для 1:1 VR180; 90 для 180×90 матеріалу
    }
}
```

Наявний `ViewMode` ([`ViewMode.cs`](../../VRClassroomPlayer/Assets/Scripts/Core/ViewMode.cs)) **лишається** як legacy-псевдонім для сумісності зі старим API/конфігами, але вся внутрішня логіка переходить на `VideoFormat`.

Мапінг legacy:

| Старий `ViewMode` | Новий `VideoFormat` |
|---|---|
| `Flat2D` | `Flat` + `Mono` |
| `Sphere360` | `Sphere360` + `Mono` |
| `None` | `None` |

### 4.2 Рядкові ідентифікатори для API

Один канонічний рядок `formatId` на сервері, в конфізі та в API:

| `formatId` | Проєкція | Стерео | Приклад джерела |
|---|---|---|---|
| `2d` | Flat | Mono | звичайний навчальний ролик |
| `360` | Sphere360 | Mono | наявний контент, поточний дефолт |
| `360_sbs` | Sphere360 | SideBySide | 360 3D SBS |
| `360_tb` | Sphere360 | TopBottom | **семпл замовника** (5760×5760) |
| `180` | Hemisphere180 | Mono | mono VR180 |
| `180_sbs` | Hemisphere180 | SideBySide | **семпл замовника** (8192×4096) |
| `180_tb` | Hemisphere180 | TopBottom | рідко, але зустрічається |
| `auto` | — | — | лише в конфізі: визначити автоматично при відкритті |

Аліаси, які парсер зобов'язаний приймати (бо вони гуляють по індустрії й по історії проєкту):
`flat`→`2d`; `sphere`, `360_mono`→`360`; `180_lr`, `180_3dh`→`180_sbs`; `360_ou`, `360_3dv`→`360_tb`; `360_lr`, `360_3dh`→`360_sbs`; `180_ou`, `180_3dv`→`180_tb`; `180_mono`→`180`.

## 5. Архітектурні варіанти

| | Варіант A — нативний Surface + OVROverlay | Варіант B — лишити Unity VideoPlayer | Варіант C — AVPro Video |
|---|---|---|---|
| Суть | Java-плагін (`MediaPlayer`/ExoPlayer) рендерить у `Surface` від `OVROverlay` (shape `Equirect`), per-eye rect для SBS/TB | Додати півсферу + стерео-шейдер, підняти клемп до 8192 | Комерційний ассет із готовою підтримкою Quest, стерео, 180/360, OVROverlay |
| 8K60 180 SBS | Реалістично | Майже напевно ні (§3, п.2) | Реалістично |
| 5.7K30 360 TB | Так | Ймовірно так, з просадками | Так |
| Якість | Найкраща (без подвійного ресемплінгу, композитор семплить напряму) | Гірша | Дуже добра |
| 10-bit | Композитор працює з нативним форматом декодера | Ріжеться до 8 біт у ARGB32 | Підтримується |
| Обсяг роботи | Великий: Java/AAR плагін, рефакторинг `VideoPlayerController` | Малий | Середній (інтеграція + ліцензія) |
| Ціна | 0 | 0 | ~$500 ліцензія |
| Ризик | Середній (нова кодова база, треба тримати редакторний фолбек) | Високий (може просто не запрацювати на цільових файлах) | Низький технічно, є юридичний/ліцензійний |

**Рекомендація:** **A**, з **B як фолбеком** для `Flat`, редактора і низькороздільного контенту. **C** — резервний план, якщо A забуксує на нативному шарі; для комерціалізації продукту це виправдана витрата.

### 5.1 Поетапність

| Фаза | Зміст | Вихід |

#### 6.1.2 `IVideoBackend`

```csharp
public interface IVideoBackend
{
    event Action<PlayerState> OnStateChanged;
    event Action<string>      OnVideoLoaded;
    event Action              OnVideoCompleted;
    event Action<int, int>    OnVideoSizeKnown;   // реальні w/h джерела

    bool  SupportsFormat(VideoFormat format, int width, int height);
    void  Open(string fullPath, VideoFormat format);
    void  Play();
    void  Pause();
    void  Stop();
    void  Seek(float seconds);
    void  SetVolume(float effective);
    bool  IsLooping { get; set; }
    float CurrentTime { get; }
    float Duration { get; }
}
```

Вибір бекенду при `Open`:

```
якщо platform != Android            → UnityVideoBackend (редактор, дебаг)
якщо projection == Flat             → UnityVideoBackend
якщо width*height > порогу (напр. 4096*2048) або stereo != Mono
                                    → NativeVideoBackend, з фолбеком на Unity при помилці
інакше                              → UnityVideoBackend
```

Поріг має бути константою в `PlayerConfig` і перевизначатись через `/video-settings`, щоб не перезбирати APK під час польових тестів.

#### 6.1.3 `NativeVideoBackend` (Phase 3) — ключові моменти

- `OVROverlay` з `isExternalSurface = true`, `externalSurfaceWidth/Height` = роздільність джерела.
- `OVROverlay.currentOverlayShape`:
  - `Equirect` для `Sphere360`;
  - для `Hemisphere180` — той самий `Equirect` із звуженим `textureRectMatrix` (source rect по горизонталі 0.25…0.75 екв. простору) **або** `Quad`/`Cylinder`, якщо Equirect не дає потрібного FOV. Перевірити на пристрої: Meta мінявся в API між версіями SDK.
- Per-eye rect: `OVROverlay.SetSrcDestRects(srcLeft, srcRight, destLeft, destRight)`:
  - SBS: left = `(0, 0, 0.5, 1)`, right = `(0.5, 0, 0.5, 1)`;
  - TB: left = `(0, 0, 1, 0.5)`, right = `(0, 0.5, 1, 0.5)` — **уточнити напрямок осі V на пристрої**, у Meta вона знизу-вгору;
  - `swapEyes` міняє local/right місцями.
- Порядок шарів: overlay має бути **underlay** (`OVROverlay.currentOverlayType = Underlay`) або підняти над сценою — залежить від того, чи лишається HUD. HUD ([`PlayerHUD.cs`](../../VRClassroomPlayer/Assets/Scripts/UI/PlayerHUD.cs)) має лишатись видимим над відео.
- Аудіо йде через нативний `MediaPlayer` ⇒ `AudioListener.volume` більше не керує гучністю. `SetVolume` має викликати `MediaPlayer.setVolume(l, r)`. Це зачіпає наявну логіку `GlobalVolume * PersonalVolume` у `VideoPlayerController`.
- `Seek`, `Duration`, `CurrentTime` — з `MediaPlayer`; врахувати, що seek у long-GOP 8K дорогий (§11).
- Життєвий цикл: пауза/фокус застосунку (`OnApplicationPause`) має коректно зупиняти нативний плеєр і звільняти `Surface`, інакше — витік і чорний екран після повернення.

#### 6.1.4 Шейдери (Phase 2, і як фолбек назавжди)

Мінімальна зміна у `VideoSphere.shader`:

```hlsl
Properties {
    ...
    _StereoLayout ("Stereo Layout (0 mono, 1 sbs, 2 tb)", Int) = 0
    _SwapEyes ("Swap Eyes", Int) = 0
}

// у фрагментному шейдері, ПІСЛЯ UNITY_SETUP_STEREO_EYE_INDEX_POST_VERTEX(i)
float2 uv = i.uv;
int eye = unity_StereoEyeIndex;
if (_SwapEyes != 0) eye = 1 - eye;

if (_StereoLayout == 1) {          // side-by-side: ліве око зліва
    uv.x = uv.x * 0.5 + eye * 0.5;
} else if (_StereoLayout == 2) {   // top-bottom: ліве око зверху
    uv.y = uv.y * 0.5 + (1 - eye) * 0.5;
}
```

Важливі нюанси:

- Розрахунок **має бути у фрагменті**, а не у вершинному: `unity_StereoEyeIndex` у вершинному шейдері при single-pass instanced доступний, але міксувати з наявним дзеркаленням `uv.x = 1 - uv.x` небезпечно — порядок операцій змінює результат для SBS. Порядок: спершу дзеркалення для inside-out, потім поділ на око.
- Наявне дзеркалення `1.0 - uv.x` у `VideoSphere.shader` + від'ємний `localScale.x = -100` у `ViewModeManager` — **дві компенсації, що взаємно накладаються**. Перед додаванням стерео обов'язково розібратись, яка з них потрібна, інакше SBS дасть перевернуті очі (найгірший можливий баг: викликає нудоту, але виглядає «майже нормально»).
- Перевірити на **обох** режимах стерео-рендерингу, які може мати проєкт (Multiview / Multi-pass): `unity_StereoEyeIndex` поводиться по-різному.
- Для `Hemisphere180` — окремий шейдер не обов'язковий, якщо меш побудований під 180° (UV 0..1 покривають півсферу). Простіший і надійніший варіант: **геометрія вирішує FOV, шейдер вирішує стерео**.

#### 6.1.5 Півсфера (`HemisphereMeshBuilder`)

- Процедурний меш: сегменти по долготі −90°…+90°, по широті −90°…+90°.
- UV: `u = (lon + 90) / 180`, `v = (lat + 90) / 180`.
- Нормалі всередину (або `Cull Front`, як у наявному сферичному шейдері).
- Роздільність меша: не менше 64×64 сегментів, інакше видно фасетки на прямих лініях (двері, стіни).
- Позаду глядача — окремий об'єкт: чорна сфера/скайбокс. Дефолт — чорний; альтернатива (м'яке згасання по краю) — див. §13, питання до замовника.
- Кешувати меш, не будувати на кожен `open`.

#### 6.1.6 Орієнтація

Для `Hemisphere180` глядач **зобов'язаний** дивитись у «перед» контенту, інакше він бачить чорноту.

- `autoRecenterOnOpen` для 180 має бути **примусовим true** незалежно від запиту (з логом), або дефолт для 180-формату — `true`. Рішення винести в конфіг відео.
- `forwardYaw` у `VideoFormat` дозволяє зсунути «перед» контенту, якщо матеріал знято з поворотом.
- [`OrientationManager.cs:117`](../../VRClassroomPlayer/Assets/Scripts/Core/OrientationManager.cs) обертає `viewModeManager.transform` — це працює і для півсфери, але `forwardYaw` треба додати до цього кута.

#### 6.1.7 Ліміти й пам'ять

- Підняти `maxDimension` з 4096 до 8192 **тільки для Unity-бекенда і тільки після Phase 0**; для нативного бекенда клемп не застосовується взагалі.
- Розглянути `RenderTextureFormat.ARGB2101010` замість `ARGB32` для 10-бітних джерел в Unity-бекенді (Phase 2).
- Логувати `SystemInfo.maxTextureSize`, доступну пам'ять, і фактичний розмір RT при кожному `open`.

## 8. Алгоритм автовизначення формату

Пріоритет — **зверху вниз**, перше спрацювання виграє. Кожен крок пише `detectionSource` і, за потреби, `warnings`.

1. **Ручне налаштування** в конфізі (`videoType != "auto"`) → використати його. `source = manual`.
2. **Суфікс імені файлу** (регістронезалежно, перед розширенням, роздільники `_`, `-`, пробіл):
   - `_180_lr`, `_180_sbs`, `_180_3dh`, `_ou`/`_tb`-варіанти, `_360_tb`, `_360_ou`, `_360_sbs`, `_360_lr`, `_360_mono`, `_2d`, `_180_mono`.
   - `source = filename`. **Це основний шлях** — обидва семпли замовника йому відповідають.
3. **Пропорції + метадані разом**:
   - Якщо метадані кажуть `StereoMode=left-right` → `stereo=sbs`; `top-bottom` → `tb`; `mono` → `mono`.
   - Порахувати аспект **на око**: SBS → `w/2 : h`; TB → `w : h/2`; mono → `w : h`.
   - Аспект на око ≈ 2:1 (±5%) → `360`; ≈ 1:1 (±5%) → `180`; ≈ 16:9 → `flat`.
   - `source = aspect+metadata`.
   - **Якщо метадані кажуть `equirectangular`, а аспект на око дає 1:1 — довіряти аспекту** і додати `warning` (саме випадок 180-семпла замовника).
4. **Лише метадані** (якщо аспект неоднозначний) → `source = metadata`, `warning` про низьку впевненість.
5. **Дефолт**: `360` mono, `warning` «формат не визначено».

Таблиця для наших двох семплів (перевірка алгоритму):

| Файл | Крок 2 (ім'я) | Крок 3 (аспект/мета) | Результат |
|---|---|---|---|
| `... - short_180_LR.mp4` | `_180_LR` → `180_sbs` ✅ | на око 4096×4096 = 1:1 → 180 ✅ (мета каже 360 ❌ → warning) | `180_sbs` |
| `..._360_TB.mp4` | `_360_TB` → `360_tb` ✅ | на око 5760×2880 = 2:1 → 360 ✅ (мета збігається ✅) | `360_tb` |

Обидва незалежні шляхи дають правильну відповідь — алгоритм самоперевіряється, і розбіжність між ними варто логувати як warning.

## 10. Логістика контенту

Числа з реальних семплів — це не гіпотетика, це те, з чим клас працюватиме щодня:

| Метрика | VR180 8K60 | 360 3D 5.7K30 |
|---|---|---|
| Бітрейт | 97.4 Мбіт/с | 101.4 Мбіт/с |
| На хвилину | 730 МБ | 761 МБ |
| 10-хвилинний матеріал | **7.3 ГБ** | **7.6 ГБ** |
| ×30 шоломів | **219 ГБ** | **228 ГБ** |

Наслідки, які фіча зобов'язана врахувати:

- **Місткість.** Quest 2 на 64 ГБ вміщає ~7 таких десятихвилинок разом із системою. Панель має показувати вільне місце на кожному пристрої і блокувати push, який не влізе.
- **Час заливки.** По USB 2.0 (~30 МБ/с) 7 ГБ — це ~4 хвилини на пристрій; послідовно на 30 шоломів — ~2 години. Треба перевірити, чи `requirements_manager` пушить паралельно, і зробити паралельним, якщо ні.
- **Прогрес.** `UpdateProgress` має показувати МБ/с і ETA, інакше вчитель вважатиме, що система зависла.
- **Перевірка цілісності.** На 7 ГБ обірваний push — реальність. Треба порівняння розміру (а краще — хешу або хоча б розмір+mtime) після заливки.
- **Опційно:** проксі-версії (нижчий бітрейт) для швидкого тесту в класі перед показом оригіналу. Обговорити із замовником.

### 11.2 Phase 0 — чек-лист верифікації на пристрої

Мінімальний тестовий APK (або тимчасова гілка коду плеєра), який:

1. Виводить `MediaCodecList` для `video/hevc`: `getSupportedWidths/Heights`, `isSizeSupported(8192,4096)`, `isSizeSupported(5760,5760)`, `areSizeAndRateSupported(8192,4096,60)`, `areSizeAndRateSupported(5760,5760,30)`, підтримувані профілі (`HEVCProfileMain10`) і рівні (`HEVCMainTierLevel61`, `HEVCHighTierLevel61`).
2. Пробує відкрити **обидва реальні семпли** через `Android MediaPlayer` у `SurfaceTexture` — просто щоб дізнатись, чи є декод і скільки кадрів на секунду він реально видає.
3. Те саме через `Unity VideoPlayer` → RT 8192×4096 — щоб виміряти, наскільки погано (для протоколу і для розмови із замовником).
4. Логує: модель пристрою (`SystemInfo.deviceModel`), версію ОС, доступну пам'ять, `SystemInfo.maxTextureSize`, `graphicsDeviceType`, поточний refresh rate.
5. Прототип `OVROverlay` Equirect із зовнішнім Surface — чи взагалі складається ланцюг.

Результат Phase 0 — короткий звіт у цій гілці (`docs/specs/phase0-device-report.md`), і **лише після нього** ухвалюється фінальний вибір A/B/C.

### 11.3 Тест-план фічі

- **Матриця форматів**: `2d` / `360` / `360_sbs` / `360_tb` / `180` / `180_sbs` / `180_tb` × (mono-джерело, SBS-джерело, TB-джерело) — переконатись, що неправильна комбінація дає видимо неправильну, але не аварійну картинку.
- **Перевірка очей**: тестовий кліп, де ліве і праве око явно різні (напис «L»/«R»). Це єдиний надійний спосіб зловити R5.
- **Глибина**: об'єкт на відомій відстані; перевірити, що стерео-паралакс не інвертований (інвертований дає «увігнутий» світ).
- **Перемикання**: 180 → 360 → 2D → 180 без перезапуску; жодних витоків RT/Surface (моніторити пам'ять).
- **Recenter** у 180: поворот на 180° і `recenter` — контент має опинитись перед очима.
- **Стан**: play/pause/seek/stop/loop/volume на кожному бекенді.
- **Мережа**: `/open` зі старим `mode`, з новими полями, зі суперечливою комбінацією.
- **Сервер**: юніт-тести `video_probe` на обох реальних семплах (зафіксувати очікувані значення з §1) — файли в `.gitignore`, тому тест має скіпатись, якщо їх немає, і запускатись, якщо є.
- **Регресія**: наявні тести `App/server/tests/test_config_adb_toggle.py`, `test_playback_controller_adb.py` — вони явно перевіряють `videoType`, їх треба оновити, не послабивши.
- **Довгий прогін**: 30+ хвилин 8K60 — термотротлінг і падіння fps.

## 12. Критерії приймання

1. Обидва реальні семпли замовника відтворюються на цільовому шоломі **зі стереоефектом і в правильній геометрії**, без ручного налаштування — досить покласти файл і натиснути «відкрити».
2. Для VR180 роздільність на око не гірша за **4096×4096** (тобто без клемпу до 4096 на весь кадр).
3. Формат визначається автоматично з імені файлу; ручне перевизначення доступне в панелі й переважає автодетект.
4. Панель показує технічні дані файлу і попередження про розбіжності метаданих.
5. Старі конфіги і старі плеєри не ламаються (§7).
6. Панель попереджає, якщо файл перевищує можливості декодера пристрою або вільне місце.
7. `PlayerAPI.md` і `docs/{en,uk}/prepare-videos.md` оновлені.
8. Тест «L/R» проходить: очі не переплутані, глибина не інвертована.

## Додаток B — парсер метаданих

Скрипти, якими зроблено цей аналіз, — база для `App/server/video_probe.py`. Логіка:

```python
# обхід боксів ISO BMFF
CONTAINERS = ("moov", "trak", "mdia", "minf", "stbl", "udta", "edts", "sv3d", "proj")
# "meta" має 4 байти version/flags перед дітьми
# "stsd" має 8 байт (version/flags + entry_count)
# visual sample entry ("hvc1"/"hev1"/"avc1") має 78 байт перед дітьми;
#     ширина/висота — big-endian uint16 за зміщенням 24 і 26

# hvcC: d[1] → profile_space(2b) | tier(1b) | profile_idc(5b)
#       d[12] → level_idc  (ділити на 30 для «L6.1»)
#       d[16]&3 → chroma_format
#       (d[17]&7)+8 → bit depth luma
#       (d[18]&7)+8 → bit depth chroma

# st3d (Spherical v2): d[4] → 0 mono, 1 top-bottom, 2 left-right, 3 custom
# sv3d/proj/equi: межі проєкції як 0.32 fixed-point
# uuid ffcc8263f8554a938814587a02521fdd (Spherical v1): XML у payload після 16 байт GUID

# fps: stts entries → timescale / delta (з mdhd)
# bitrate: розмір mdat * 8 / тривалість
```

Повні робочі скрипти лежать поза репозиторієм (згенеровані під час аналізу) — при реалізації їх треба переписати як модуль із тестами, а не копіювати як є.
